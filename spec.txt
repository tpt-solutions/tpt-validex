**Status:** Draft / RFC

## 1. Executive Summary

`tpt-validex` is a blazing-fast, universal, embeddable data validation engine written in pure Rust with a **minimal dependency philosophy** and **Apache-2.0-only dependency prohibition**.

Currently, every API, data pipeline, and application needs to validate incoming data (JSON payloads, CSV rows, user input, database records). But the existing solutions have major problems:
- **Python (`pydantic`, `jsonschema`):** Slow for bulk validation. `pydantic` is great for single objects, but validating 1 million JSON records takes seconds.
- **JavaScript (`zod`, `ajv`):** Runtime overhead. `zod` is ergonomic but slow. `ajv` is fast but JS-only.
- **Rust (`valico`, `jsonschema`):** Pull in many dependencies. Not optimized for streaming validation.
- **Language-specific:** You need a different validator for Python, Node.js, Go, Rust. Each has different APIs and behaviors.

`tpt-validex` solves this by providing a single, embeddable validation engine that:
- Validates millions of records per second using SIMD-optimized JSON parsing.
- Compiles schemas to state machines for O(1) validation overhead.
- Works identically across Python, JavaScript, Go, C++, and Rust.
- Supports JSON Schema (Draft 2020-12), custom DSL schemas, and streaming validation.
- Integrates seamlessly with `tpt-streamforge` for ETL pipeline validation.

**Key differentiator:** We reject heavy validation frameworks and Apache-2.0-only dependencies. We build our own minimal, SIMD-optimized schema compiler that turns validation rules into blazing-fast state machines.

## 2. Core Design Principles

1. **Strict MIT / Apache-2.0 Licensing:** All code is dual-licensed MIT / Apache-2.0. All dependencies are audited via `cargo-deny`. Any dependency carrying a copyleft license is strictly rejected.
2. **Apache-2.0-Only Dependencies Prohibited:** Dependencies that are Apache-2.0-only (not dual-licensed with MIT) are strictly rejected. We prefer MIT-only or MIT/Apache-2.0 dual-licensed dependencies. When no suitable MIT-licensed dependency exists, we build our own implementation.
3. **Minimal Dependency Tree:** We avoid heavy validation frameworks. The `jsonschema` crate is rejected due to its large transitive dependency tree. We build our own schema compiler.
4. **SIMD-Optimized Parsing:** Uses SIMD instructions (via `sonic-rs`, MIT-licensed) for JSON parsing. Achieves 10x faster parsing than `serde_json` for large payloads.
5. **Schema Compilation:** Schemas are compiled to state machines at load time. Validation is O(1) per field, not O(n) per rule.
6. **Streaming Validation:** Can validate CSV, JSON, JSONL in streaming fashion without loading entire files into memory.
7. **Multi-Language Native:** Pure Rust core with clean C ABI. Wrappers for Python, JavaScript/WASM, Go, and C/C++.
8. **Zero-Copy Where Possible:** Validates data without copying it. Passes raw pointers to the validator.

4.2 Schema Compilation Process

1. User provides a schema (JSON Schema or custom DSL).
2. Schema is parsed and validated (using custom parser, no external deps).
3. Schema is compiled to an intermediate representation (IR).
4. IR is optimized (e.g., merge redundant checks, pre-compute regex).
5. IR is compiled to a state machine (a tree of validation nodes).
6. State machine is cached for reuse.
7. Validation: data is passed through the state machine, field by field.

This compilation happens once at load time. Subsequent validations are O(1) per field.
5. Key Components & Implementation Details
5.1 Schema Compiler (tpt-valid-schema)
Supported Schema Formats:
JSON Schema (Draft 2020-12): Full support for type, properties, required, minimum, maximum, pattern, enum, format, etc.
Custom DSL: A simpler, more ergonomic schema language for common use cases.
Custom DSL Example:

let schema = validex::schema! {
    object {
        required "name" => string(min_length=1, max_length=100),
        required "age" => integer(min=0, max=150),
        optional "email" => string(format="email"),
        optional "tags" => array(items=string(), min_items=0, max_items=10),
    }
};

Schema Compilation:
Parses schema into an AST (custom parser, no external dependencies).
Validates schema semantics (e.g., min must be <= max).
Compiles AST to IR (intermediate representation).
Optimizes IR (e.g., pre-compile regex patterns).
Compiles IR to state machine (tree of validation nodes).
5.2 State Machine (tpt-valid-core)
The state machine is a tree of validation nodes:

enum ValidationNode {
    CheckType(DataType),
    CheckField(String, Box<ValidationNode>),
    CheckRequired(Vec<String>),
    CheckMinimum(f64),
    CheckMaximum(f64),
    CheckPattern(Regex),
    CheckEnum(Vec<Value>),
    CheckFormat(Format),
    CheckArray(Box<ValidationNode>, usize, usize),
    CheckObject(Vec<(String, ValidationNode)>),
}

Validation Process:
Start at root node.
For each field in the data, traverse the tree.
At each node, perform the check (e.g., CheckType(Integer)).
If check fails, collect error and continue (to report all errors, not just the first).
Return list of errors (empty if valid).
Performance Optimization:
State machine is compiled once, reused for all validations.
Regex patterns are pre-compiled (using regex crate, MIT/Apache-2.0 dual-licensed).
Enum checks use hash sets for O(1) lookup.
Array/object checks are unrolled for small sizes.
5.3 SIMD-Optimized Parser (tpt-valid-parser)
JSON Parsing:
Uses sonic-rs (MIT-licensed) for SIMD-accelerated parsing.
Achieves 10x faster parsing than serde_json for large payloads.
Falls back to jiter (MIT-licensed) if sonic-rs is unavailable.
Falls back to serde_json (MIT/Apache-2.0 dual-licensed) as the guaranteed-compatible baseline.
All JSON parsing dependencies are MIT-licensed or MIT/Apache-2.0 dual-licensed. No Apache-2.0-only dependencies.
CSV Parsing:
Custom streaming CSV parser (built from scratch, zero external dependencies).
Handles quoted fields, custom delimiters, type inference.
Validates each row against the schema.
JSONL Parsing:
Custom streaming parser (built from scratch, zero external dependencies).
Validates each line independently.
Reports errors with line numbers.

5.5 Validation Engine (tpt-valid-core)
Validation Modes:
Single Object: Validate a single JSON object.
Batch: Validate a list of objects in parallel (using rayon, MIT/Apache-2.0).
Streaming: Validate a stream of objects (CSV, JSONL) without loading into memory.

Collects all errors, not just the first.

5.6 Streaming Validation (Integration with tpt-streamforge)
tpt-validex can be used as a transformation stage in tpt-streamforge:

use tpt_streamforge::Pipeline;
use tpt_validex::Schema;

let schema = Schema::from_json_schema(json_schema)?;

let pipeline = Pipeline::new()
    .read_csv("input.csv")
    .validate(&schema)  // Validates each row, filters out invalid rows
    .write_csv("valid_output.csv")
    .write_errors("errors.jsonl");  // Writes validation errors to separate file

pipeline.execute()?;

This allows ETL pipelines to validate data on-the-fly, filtering out invalid records and logging errors.
6. Target API Design (Developer Experience)
6.1 Python API (via PyO3)

from tpt_validex import Validator

# Load a JSON Schema
schema = {
    "type": "object",
    "properties": {
        "name": {"type": "string", "minLength": 1},
        "age": {"type": "integer", "minimum": 0, "maximum": 150},
        "email": {"type": "string", "format": "email"}
    },
    "required": ["name", "age"]
}

validator = Validator(schema)

# Validate a single object
data = {"name": "Alice", "age": 30, "email": "alice@example.com"}
is_valid, errors = validator.validate(data)
print(f"Valid: {is_valid}, Errors: {errors}")

# Validate a batch of objects (parallel)
batch = [
    {"name": "Alice", "age": 30},
    {"name": "Bob", "age": "25"},  # Invalid: age is string
    {"name": "", "age": 200},      # Invalid: name too short, age too high
]
results = validator.validate_batch(batch)
for result in results:
    print(f"Valid: {result.is_valid}, Errors: {result.errors}")

# Validate a CSV file (streaming)
validator.validate_csv("input.csv", valid_output="valid.csv", errors_output="errors.jsonl")

6.4 C API (via FFI)

#include "tpt_validex.h"

int main() {
    const char* schema = "{\"type\": \"object\", \"properties\": {\"age\": {\"type\": \"integer\"}}}";
    
    tpt_valid_handle* validator = tpt_valid_create(schema);
    
    const char* data = "{\"age\": 25}";
    tpt_valid_result* result = tpt_valid_validate(validator, data);
    
    if (tpt_valid_is_valid(result)) {
        printf("Valid!\n");
    } else {
        printf("Invalid: %s\n", tpt_valid_get_errors(result));
    }
    
    tpt_valid_free_result(result);
    tpt_valid_destroy(validator);
    return 0;
}

9. Open Questions & Risks
JSON Schema Compliance: JSON Schema is complex. Full compliance with Draft 2020-12 is a large undertaking. Mitigation: Start with the most common features (type, properties, required, min/max, pattern). Add advanced features (if/then/else, allOf/anyOf/oneOf) in Phase 2. Document supported features clearly.
SIMD Availability: SIMD is not available on all platforms (e.g., WASM). Mitigation: Fall back to jiter (MIT) or serde_json (MIT/Apache-2.0) if SIMD is not available. Document performance differences.
Custom DSL vs. JSON Schema: Should we support both, or just one? Mitigation: Support JSON Schema for compatibility. Add custom DSL as an optional, more ergonomic alternative in Phase 8.
Error Reporting: Should we report all errors, or stop at the first? Mitigation: Default to reporting all errors (more useful for debugging). Add a "fail-fast" mode for performance-critical use cases.
Transitive Dependency Drift: A currently permissive dependency could add a copyleft or Apache-2.0-only transitive dependency. Mitigation: cargo-deny runs on every PR and every release tag. Pin dependency versions in Cargo.lock. Explicitly check for Apache-2.0-only dependencies.
Integration with tpt-streamforge: How do we handle invalid rows in a streaming pipeline? Mitigation: Write invalid rows to a separate error file. Allow users to configure error handling (skip, abort, log).
Custom Format Validators: Building email/URI/UUID validators from scratch is complex. Mitigation: Start with basic implementations. Use well-known test vectors to validate correctness. Add edge cases over time.

13. Example Use Cases
Use Case 1: API Request Validation

from fastapi import FastAPI
from tpt_validex import Validator

app = FastAPI()

schema = {
    "type": "object",
    "properties": {
        "name": {"type": "string", "minLength": 1},
        "age": {"type": "integer", "minimum": 0, "maximum": 150},
    },
    "required": ["name", "age"]
}

validator = Validator(schema)

@app.post("/users")
async def create_user(request: dict):
    is_valid, errors = validator.validate(request)
    if not is_valid:
        return {"error": "Invalid data", "details": errors}
    # ... create user

Use Case 3: Browser-Side Form Validation

import { Validator } from 'tpt-validex';

const schema = {
  type: 'object',
  properties: {
    email: { type: 'string', format: 'email' },
    password: { type: 'string', minLength: 8 },
  },
};

const validator = new Validator(schema);

document.getElementById('form').addEventListener('submit', (e) => {
  e.preventDefault();
  const data = {
    email: document.getElementById('email').value,
    password: document.getElementById('password').value,
  };
  
  const { isValid, errors } = validator.validate(data);
  if (!isValid) {
    // Show errors to user
    console.error('Validation errors:', errors);
  } else {
    // Submit form
    e.target.submit();
  }
});
